#### DRF view runtime (`plane-drf`)

The per-route policy is generated from Django's own introspection
(`tools/inventory/routes.py` records `base_family`, `use_read_replica`,
`TimezoneMixin`, `http_method_names`, parser/renderer/metadata classes,
`get_view_name()`/`get_view_description()`, lifecycle overrides,
`allow_permission` per method, the `BaseViewSet` guard's action half and the
`OPTIONS` action field maps). `crates/plane-drf` embeds `routes.json`, refuses
to start on an unknown class or an unimplemented override, and is the only way
a handler becomes reachable: `Registry::viewset(...).action(...)` /
`api_view(...).method(...)` / `django_view` / `function`, with paths, methods
and every security class taken from the table. Dispatch reproduces
`APIView.initial` order (negotiation → authenticators → permissions →
throttles → timezone → family `initial` → `allow_permission` → handler),
`handle_exception` per family and `finalize_response` (`Allow` in
`http_method_names` order, `X-RateLimit-*` on `/api/v1/`). Plain Django views
and function views skip DRF entirely and use `View.dispatch`.

Verification: `scenarios/policy-probe.yaml` (5,451 steps; generated by
`tools/policy/gen_policy_scenario.py`, fixture by `gen_fixture.py`) run with
`plane-api --features policy-probe`:

```sh
cargo build -p plane-api --features policy-probe
./target/debug/difftest run --scenario scenarios/policy-probe.yaml --a django --b rust
```

The harness treats a B response carrying `X-Plane-RS-Probe: handler` as a
pass-through: if A denied at the policy (401/405/406/415/429, or a 403 with one
of the policy bodies) it is a DIFF; otherwise the step is `reached-handler` and
its response and DB/Redis/Celery side effects are ignored. Redis keys written
by a reached-handler step are remembered and excluded from later steps (their
TTL would otherwise change on A alone). Writes are the final block; `DELETE`
steps name objects that do not exist, and the four routes that destroy shared
state (user deactivate, workspace delete, project/workspace leave) run only
against per-route disposable objects.

Result (2026-11-16, two consecutive runs, Django vs `plane-api
--features policy-probe`): **5,451 steps; 2,287 policy denials compared; 2,555
reached-handler; 0 mismatches; exit 0 both times.** `skeleton.yaml` (Django vs
Rust) and `auth-session.yaml` (Django vs Django, as its header says until
Phase 6) still pass.

- `HEAD` of a response without `Content-Length`: uvicorn sends `Transfer-Encoding: chunked`, hyper sends neither header.

## Open questions for the owner

1. `SECRET_KEY` unset: Django falls back to a random key per process (sessions and encrypted
   instance configuration then break across processes). Default taken: Rust does the same
   and logs the same critical message, because behaviour must match. Say if Rust should
   refuse to start instead.
2. Scout APM (`SCOUT_MONITOR`, `SCOUT_KEY`) is a Python agent. Default taken: not ported;
   the variables are accepted and ignored.
3. boto3 resolves S3 credentials through its full chain (env, profile files, instance
   roles). Default taken: the Rust client supports env credentials plus the container and
   instance metadata providers; profile files only if a deployment needs them. Decide at
   Phase 5.
4. Celery arguments: some callers pass UUID objects (serialised as kombu
   `{"__type__":"uuid",...}` envelopes), others strings. Default taken: the Rust publisher
   reproduces each call site's types exactly.

## Suspected upstream bugs, ported as they are

- `GET /api/workspaces/` returns 400 `{"error": "The required key does not exist."}`:
  `allow_permission` reads `kwargs["slug"]` on a route without it
  (`plane/app/permissions/base.py:62`). The web app uses `/api/users/me/workspaces/`.
- A CSRF rejection on Django form views returns 200 with an HTML page
  (`plane/authentication/views/common.py:39-45`).
- The admin session cookie is chosen by `"instances" in request.path`, a substring test
  (`plane/authentication/middleware/session.py:23,43`).
- `APPEND_SLASH` answers a POST with 301 and drops the body at `DEBUG=0`.
- With `NUM_PROXIES` unset, the throttle identity collapses `X-Forwarded-For`, so clients
  behind a proxy share one bucket (`rest_framework/throttling.py:40`).
- Pages: `project_ids` aggregates over the visibility join, so it lists projects whose
  `ProjectPage` link is soft-deleted, and its `~Q(projects__id=True)` filter compiles to a
  sentinel UUID comparison (`plane/app/views/page/base.py:127-140`). `label_ids` ignores
  `page_labels.deleted_at`. The visibility join ignores `project_members.deleted_at`.
  `live-access` answers 404 on every denial and matches `action` case-sensitively
  (`plane/app/views/page/live.py`).
- Assets: `/api/workspaces/{slug}/file-assets/`, `/api/users/file-assets/` and the
  collection shapes of the v2 workspace/project asset routes always return 500, because
  their URL patterns don't pass the arguments the shared `get` needs
  (`plane/app/views/asset/base.py:27,87`, `v2.py:496,721`). `UserAssetsEndpoint.get`
  serialises a queryset without `many=True` (`base.py:90`). The Unsplash search URL has a
  literal `$page` (`plane/app/views/external/base.py:235`). `attributes.get("name",
  uuid4().hex)` gives a different download filename on each request when the name is
  missing (`v2.py:987,1022`). The attachment detail never checks `entity_type`, and the
  attachment list never checks that the issue belongs to the project
  (`plane/app/views/issue/attachment.py:212-238`).
- Intake: the list defaults `?status=-2`, so it only lists pending items; `?status=`
  (empty) is a 500 (`plane/app/views/intake/base.py:208-210`). A project without an intake
  renders `IntakeSerializer.get_initial()`, while retrieve dereferences `None` → 500
  (`:76-77`, `:509-510`). `pending_issue_count` counts soft-deleted rows (`:70`).
- Notifications: `mentioned=false` filters *for* mentions (any non-empty string is
  truthy), `?type=` with an unknown value returns everything, `snoozed=true`/`false`
  overlap, pagination needs both `per_page` and `cursor`
  (`plane/app/views/notification/base.py:55-141`). The preference GET is a 500 when a user
