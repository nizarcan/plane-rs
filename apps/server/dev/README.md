# Local dev stack for the Rust rewrite

Infrastructure and helpers for running Django (`apps/api`) and, later, the Rust
services against one throwaway local stack. Everything here binds to
`127.0.0.1` on the ports reserved in `apps/server/AGENTS.md`; nothing touches the
machine's unrelated containers (5432, 6379, 9000, 9001, 9092, 6390).

The Docker VM has 2 CPUs and about 2 GB of memory, so the stack is deliberately
lean: Postgres 384 MB, RabbitMQ 320 MB, MinIO 256 MB, Valkey 64 MB. Never start
`docker-compose-local.yml` or `docker-compose-test.yml` alongside it.

## Ports and services

| Service | Image | Host endpoint | Memory limit |
| --- | --- | --- | --- |
| Postgres | `postgres:15.7-alpine` | `127.0.0.1:55432` | 384 MB |
| Valkey | `valkey/valkey:7.2.11-alpine` | `127.0.0.1:56379` | 64 MB |
| RabbitMQ | `rabbitmq:3.13.6-management-alpine` | `127.0.0.1:55672` AMQP, `127.0.0.1:55673` management | 320 MB |
| MinIO (Silo) | `docker.io/pgsty/silo:RELEASE.2026-09-16T00-00-00Z` | `127.0.0.1:59000` S3, `127.0.0.1:59090` console | 256 MB |

Postgres runs as `plane`/`plane` with database `plane`, `max_connections=500`
and the usual dev-speed settings (`fsync`, `synchronous_commit` and
`full_page_writes` off). `pgdata` is a named volume, so `plane_tpl` and the
databases cloned from it survive `down.sh` and restarts. RabbitMQ has user
`plane`/`plane` and vhost `plane`; MinIO has `access-key`/`secret-key` and
creates the `uploads` bucket on every start.

Other port ranges are reserved and must not be used by these scripts: Django
instances 18000-18099, Rust `plane-api` instances 18100-18199, the future Caddy
dev proxy 18080. `django-env.sh` points `WEB_URL` at `http://127.0.0.1:18080`
even before Caddy exists, because that is the URL the frontends will use.

## Scripts

All scripts are bash, idempotent where that makes sense, and driven from the
repo root or anywhere else. `lib.sh` holds the shared constants (ports, paths,
credentials), loads `dev/.env.local`, and must be sourced by the others, not
executed.

| Script | What it does |
| --- | --- |
| `up.sh` | `docker compose up -d --wait`, so it returns only when all four healthchecks pass. Then ensures the RabbitMQ vhost `plane` exists with permissions. Safe to re-run. |
| `down.sh` | Stops and removes the containers, keeps the named volumes. `--purge` also deletes the volumes (next start is empty; `bootstrap.sh --force` is then required). |
| `status.sh` | Prints `docker compose ps`, a health summary, and the connection endpoints. Exits 1 unless all four services are healthy, so it can gate other scripts. |
| `django-env.sh` | Prints (when executed) or exports (when sourced) the environment Django needs. See the table below. |
| `django.sh <args>` | Runs `apps/api/.venv/bin/python manage.py <args>` from `apps/api` with that environment. |
| `django-serve.sh <port>` | Serves Django in the foreground exactly as `apps/api/bin/docker-entrypoint-api.sh` does after its setup steps: gunicorn 23 with one `uvicorn.workers.UvicornWorker`, `plane.asgi:application`, bound to `127.0.0.1:<port>`, access log on stderr. No `--max-requests`, no registration/collectstatic. |
| `mq-vhost.sh <vhost>` | Creates a RabbitMQ vhost and grants `plane` configure/write/read on it. Idempotent. `--delete [--force]` removes it; the shared `plane` vhost needs `--force`. |
| `bootstrap.sh [--force]` | Builds the `plane_tpl` template database. Does nothing if it already exists, unless `--force` drops and rebuilds it. |
| `mkdb.sh <name> [--replace]` | Clones `plane_tpl` as `<name>`. Refuses an existing name unless `--replace` (which drops it first). |
| `dropdb.sh <name>` | Drops a clone, terminating open connections. Idempotent. Refuses `plane_tpl`, `plane` and the Postgres built-ins. |

`dev/.env.local` is generated by `lib.sh` on first use with a random
`SECRET_KEY`. It is gitignored and must never be committed. Delete it only if
you also rebuild the template: `InstanceConfiguration` rows are encrypted with
this key, so a new key makes `bootstrap.sh`'s output unreadable and requires
`bootstrap.sh --force`.

`dev/logs/` and `dev/run/` are gitignored scratch space for background servers
and their PID/log files.

## Typical flow

```bash
# 1. Bring the infrastructure up and wait for it.
apps/server/dev/up.sh
apps/server/dev/status.sh

# 2. Build the shared template database (only once; idempotent).
apps/server/dev/bootstrap.sh

# 3. Clone the template for your own work.
apps/server/dev/mkdb.sh t_mytask_1

# 4. Serve Django against the clone. Foreground; Ctrl-C stops it.
PLANE_DB=t_mytask_1 apps/server/dev/django-serve.sh 18000

# 5. In another shell: a smoke request.
curl -si http://127.0.0.1:18000/api/instances/

# 6. Management commands against the clone.
PLANE_DB=t_mytask_1 apps/server/dev/django.sh showmigrations --plan
PLANE_DB=t_mytask_1 apps/server/dev/django.sh shell

# 7. Clean up your database when done.
apps/server/dev/dropdb.sh t_mytask_1
```

To use the environment in your own shell or from a non-bash tool:

```bash
eval "$(apps/server/dev/django-env.sh)"
# or, inside bash:
source apps/server/dev/django-env.sh
```

## What `bootstrap.sh` puts in `plane_tpl`

The template mirrors what `apps/api/bin/docker-entrypoint-api.sh` does on a fresh
instance, restricted to database state:

1. `CREATE DATABASE plane_tpl`
2. `manage.py migrate`
3. `manage.py register_instance plane-rs-dev-template` (fixed dev signature;
   `register_instance` enqueues `push_instance_metrics` to RabbitMQ, so the
   broker must be healthy)
4. `manage.py configure_instance` (reads the `ENABLE_*`/OAuth/SMTP/LLM values
   from the environment; encrypted values use `SECRET_KEY`)
5. `manage.py create_bucket` (creates `uploads` in MinIO; already exists
   because the container creates it on start)

`clear_cache` and `collectstatic` are not run: they touch shared Redis and the
static tree, not the database, and `django-serve.sh` does not need them.

At this commit the result contains 167 migration rows, exactly one `instances`
row and 36 `instance_configurations` rows, and **no users or workspaces**. It is
marked `IS_TEMPLATE true` and `ALLOW_CONNECTIONS false`, so nothing can write to
it by accident. To inspect it, clone it (`mkdb.sh t_inspect`) and query the
clone. `mkdb.sh` terminates any stray session before cloning, so a leftover
connection cannot block it.

On this repo the migration count was verified as
`SELECT count(*) FROM django_migrations` = 167 = `showmigrations --plan | grep -c '\[X\]'`
on a clone. Re-check both if the Python schema changes: the template must be
rebuilt after new Django migrations (`bootstrap.sh --force`).

## Environment set by `django-env.sh`

`DJANGO_SETTINGS_MODULE=plane.settings.production` matches `manage.py`, `wsgi.py`,
`asgi.py`, `celery.py` and `apps/api/Dockerfile.api`'s entrypoint. `DEBUG=0`
keeps the served behaviour (caching, error pages) close to a real deployment.

| Variable | Why |
| --- | --- |
| `DJANGO_SETTINGS_MODULE`, `DEBUG`, `IS_TEST` | production settings, debug off, not a test instance |
| `SECRET_KEY` | sessions, CSRF, password-reset tokens and the Fernet key for encrypted `InstanceConfiguration` rows |
| `DATABASE_URL` | parsed by `plane/settings/common.py`; `PLANE_DB` selects the database |
| `ENABLE_READ_REPLICA=0` | keeps the read-replica router out of the dev environment |
| `REDIS_URL` | django-redis cache and rate-limit store; `PLANE_REDIS_DB` selects the logical DB |
| `RABBITMQ_HOST/PORT/USER/PASSWORD/VHOST` | `CELERY_BROKER_URL` is built from these |
| (`AMQP_URL` unset) | it would override the `RABBITMQ_*` variables and point Celery elsewhere |
| `WEB_URL` | S3 custom domain and `Secure`-cookie decision |
| `ALLOWED_HOSTS=*` | dev-only; the same default `common.py` uses |
| `USE_MINIO`, `MINIO_ENDPOINT_SSL=0` | selects the path-style MinIO client in `plane/settings/storage.py` |
| `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_S3_BUCKET_NAME`, `AWS_S3_ENDPOINT_URL`, `AWS_REGION` | object storage and `create_bucket`; MinIO ignores the region but SigV4 needs one |
| `SIGNED_URL_EXPIRATION` | presigned upload/download lifetime |
| `GUNICORN_WORKERS=1` | read by `django-serve.sh`; small enough for the memory budget |
| `PYTHONDONTWRITEBYTECODE`, `PYTHONUNBUFFERED` | no `.pyc` churn in `apps/api`, streaming logs |
| `ENABLE_DRF_SPECTACULAR=0` | pinned off so a caller's shell cannot slow every command down |
| `PLANE_DB`, `PLANE_REDIS_DB`, `PLANE_MQ_VHOST` | the isolation knobs, passed through |
| (`SCOUT_MONITOR`, `SCOUT_KEY` unset) | `production.py` installs `scout_apm`; any non-empty value would try to report |

`django-env.sh` does not modify `apps/api`: the only files it causes Django to
write are `apps/api/logs/` and Python caches, both already gitignored generated
artefacts.

### gunicorn

`apps/api/.venv` is synced with the `dev` and `test` groups, but gunicorn lives
in the `production` group. If `django-serve.sh` reports that gunicorn is
missing, add only that package to the existing venv (do not re-sync the whole
environment):

```bash
cd apps/api
uvx --from 'uv==0.12.21' uv pip install --python .venv/bin/python 'gunicorn==23.0.0'
```

## Isolation for concurrent agents

Several agents share this stack. Never serve against or migrate the shared
template; give yourself three unique names:

| Resource | Knob | Convention | Cleanup |
| --- | --- | --- | --- |
| Postgres database | `PLANE_DB` | `t_<task>_<n>`, cloned with `mkdb.sh` | `dropdb.sh t_<task>_<n>` |
| Redis logical DB | `PLANE_REDIS_DB` (0-15) | one index per agent; `0` is the default and shared | flush only your index (`valkey-cli -n <n> FLUSHDB`), or leave it to the 32 MB LRU |

Redis caches DRF responses by request path (`plane/utils/cache.py`), not by
database, so two agents on the same Redis index can see each other's cached
bodies (for example `/api/instances/` from a different clone). Use a distinct
index whenever you compare responses.
| RabbitMQ vhost | `PLANE_MQ_VHOST` | `t_<task>_<n>`, created with `mq-vhost.sh` | `mq-vhost.sh --delete t_<task>_<n>` |
| Django port | `django-serve.sh <port>` | 18000-18099 | kill the foreground process |

Example:

```bash
apps/server/dev/mkdb.sh t_diff_1
apps/server/dev/mq-vhost.sh t_diff_1
PLANE_DB=t_diff_1 PLANE_REDIS_DB=4 PLANE_MQ_VHOST=t_diff_1 \
  apps/server/dev/django-serve.sh 18001
# ... work ...
apps/server/dev/dropdb.sh t_diff_1
apps/server/dev/mq-vhost.sh --delete t_diff_1
```

Do not delete `plane_tpl` or the `plane` vhost, and do not run `down.sh` or
`down.sh --purge` while other agents are using the stack. If the stack is
unhealthy, check `status.sh` first; rebuilding the template affects everyone and
is the orchestrator's call unless you are alone.

## Troubleshooting

- **A service is `unhealthy` or keeps restarting** — look at its logs with
  `docker compose -f apps/server/dev/compose.yml -p plane-rs-dev logs <service>`.
  RabbitMQ is the slowest to become healthy (Erlang boot, ~10-20 s).
- **Postgres volume is corrupted or the template is wrong** — `down.sh --purge`
  then `up.sh` and `bootstrap.sh --force`. This deletes every clone, so only do
  it when nobody else is working.
- **`create_bucket` fails** — check `mc ls local/uploads` inside the MinIO
  container; the healthcheck only reports healthy once the bucket exists.
- **`CREATE DATABASE ... TEMPLATE` blocks** — `mkdb.sh` terminates sessions on
  the template first. If it still blocks, someone connected to `plane_tpl`
  manually after enabling connections; close it and retry.
- **Django starts with `No directory at: .../collected-static/`** — expected,
  `collectstatic` is not part of `django-serve.sh`; static files are not served
  by the backend in this setup.
- **`bootstrap.sh` says the template exists but its contents look stale** —
  rebuild with `--force`; it is a snapshot, not a live database.
